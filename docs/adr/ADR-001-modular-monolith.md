# ADR-001:以模块化单体承载全部验证链路

## 状态

已接受

## 日期

2026-08-17（追溯记录：该决策在项目启动时即已生效，此前只散见于 `docs/architecture.md`，未单独立档）

## 背景

PatchAtlas 的验证链路跨越多种异质能力：Git 仓库获取、受限 Docker 执行、Surefire 报告解析、模型调用、可恢复的 Run 持久化与可观测性。这些能力在部署形态上有天然的拆分诱因——沙箱执行是 CPU 与磁盘密集的，模型调用是网络密集且高延迟的，REST 读取是低延迟的。

但项目要证明的核心命题不是"这些能力能否分布式协作"，而是"**一个候选测试是否真的复现了缺陷**"。该命题的可信度取决于执行隔离、失败分类、稳定性归约与预言机隔离，这些都是单进程内就能做对或做错的事。

如果一开始就拆成多服务，团队会把预算花在服务发现、跨进程事务、重试幂等与链路追踪上，而这些工作**不会让复现裁决更可信**。

## 决策

初期使用**一个 Spring Boot 服务加一个 Vue 应用**，后端按包划分模块并显式约束依赖方向：

```text
run → agent / replay / repository / sandbox
observability → run（单向）
```

模块边界靠**包边界与类型可达性**维持，而不是靠网络边界。特别地，预言机隔离（生成器不得取得 Fixed Revision）由 `CaseManifest` 在类型层拆分保证，`agent` 包在编译期就够不到 Oracle Data——这比跨服务的"约定不要传这个字段"更强。

尚未出现真实调用链的模块不提前创建空接口或空包。

## 考虑过的替代方案

### 一开始就拆分微服务

优点是各能力可独立扩缩容，沙箱执行的资源占用不会影响 REST 响应。缺点是它把项目的主要风险从"复现是否可信"转移到"服务间通信是否可靠"，而后者不是本项目要回答的问题。跨进程之后，预言机隔离要靠序列化契约维持，比类型层保证弱；崩溃恢复要引入分布式事务或补偿，而单进程内一个带 fence 的数据库租约就够了。

### 单体但不约束依赖方向

实现成本最低，但会让 `agent` 包在某次重构后意外取得 Fixed Revision，而这种破防**不会有任何测试报错**——它只会让 Benchmark 结果悄悄失去意义。显式依赖方向加上类型层的 Oracle 拆分，是让编译器替人守边界。

### 单体 + 插件化运行时

用 SPI 或动态加载让沙箱执行器可替换。它比拆服务轻，但仍然引入类加载与版本兼容问题，而当前只有一种沙箱实现需要在生产运行——按"一个 adapter 是假 seam，两个才是真 seam"的标准，此时的可替换性是想象出来的需求。

## 后果

- 部署与本地启动简单，一个数据库加一个进程即可跑通全链路；
- 预言机隔离由编译器保证，是本项目最强的一条不变量；
- 沙箱执行会占用与 Web 请求同一个进程的宿主资源，因此 REST 入口被设计成异步命令：落库后返回 `202 Accepted`，不在 HTTP 请求中等待模型、Git 或 Docker；
- 水平扩展受限。跨进程并发目前由数据库的 claim、lease 与 fence 承担，这在单用户自托管场景下足够；
- **该决策不排除把单一能力提取为独立进程**。当某个能力出现了单体内无法满足的约束（例如沙箱执行需要 Docker Socket，而应用容器不应持有它），可以为它单独立 ADR，把该能力移出进程，而不必推翻本决策。
